# Feature: Matt Pocock Skills Expansion + Close-Out PR Skill

![Status: Completed](https://img.shields.io/badge/status-Completed-brightgreen)

## Introduction

**Status:** Completed 2026-11-02 — batches A–I are implemented (T1–T30).

The template already vendors five of Matt Pocock's scoping skills at `v1.3.1` (`grilling`, `grill-me`, `grill-with-docs`, `domain-modeling`, `prototype`) and drives them through the `scope` agent. That set stops at "narrow the problem". It has no way to plan work larger than one session, no way to turn a settled decision into tickets or a spec, and no way to close out a branch (commit, push, open a PR) short of the ad-hoc `.opencode/commands/github-pr.md`, which hardcodes base `main` (`.opencode/commands/github-pr.md:28`).

This plan closes those three gaps by delivering seven skills, a tracker declaration, and the command the vendored skills tell users to run:

1. **Vendor five more upstream skills at `v1.3.2`** — `wayfinder`, `to-tickets`, `to-spec`, `pr`, `research` — byte-verbatim, with pin + hashes in `skills-lock.json`.
2. **Add two repo-local skills** — `to-pr` (real commit/push/PR work) and `close-out` (a human-invoked trigger wrapper around `to-pr`).
3. **Declare a tracker** — `.agents/config/issue-tracker.md` names GitHub Issues, defines the six labels, and specifies how wayfinding maps, tickets, and blocking edges are expressed. Setup creates the labels.
4. **Ship `/setup-matt-pocock-skills`** — the command `wayfinder` (`SKILL.md:25`), `to-tickets` (`SKILL.md:11`), and `to-spec` (`SKILL.md:9`) tell the user to run when no tracker is configured.

Sketching tickets in a tracker nobody configured is what the `research` skill and the setup command exist to prevent. This revision reverses the earlier documentation-only decision (see D-07 and the Revision History): `wayfinder` names both artifacts by name, so shipping them is cheaper than teaching every consumer to translate a substitute.

Because the pin moves from `v1.3.1` to `v1.3.2`, `grilling`'s vendored bytes and hash change too (upstream edited it in `v1.3.2`). That re-vendor is in scope and called out in T5/T14.

**In scope:** the five vendored skills, two repo-local skills, the setup command, tracker doc + label creation, orchestrator/deployer/scope wiring, lock entries, docs, verification.

**Out of scope:** re-vendoring `to-pr` from an upstream tag (`to-pr` does not exist upstream), any change to the pipeline agent set (no new agents are added), any rewriting of vendored bytes, and any file-distribution work inside the new command (CON-12).

**Consequence to accept up front:** the skill count becomes **41** (34 + 7), not 38 — `to-pr`, `close-out`, and `research` are shipped skills that live in `.agents/skills/`, so they count. Every doc task below uses 41 and every count is re-derived from disk before it is written (see D-04, RISK-01).

## Design Decisions

| # | Decision | Rationale |
|---|----------|-----------|
| D-01 | Pin to `v1.3.2` (`d1478fcb140db0b93c0c8df17bcfd311844749d0`) and accept the `grilling` re-vendor | User decision. Bumping the pin without re-vendoring `grilling` would leave the lock lying about one file |
| D-02 | `to-pr` is repo-local, `pr` is vendored and used only as the body-shape reference | Upstream `pr` is a template with no execution step; the real work (commit/push/PR) must live in a skill this repo owns and can wire to `deployer` |
| D-03 | Tracker is GitHub Issues; maps and tickets are issues with `wayfinder:*` labels; blocking edges are plain `Blocked by: #N` lines | The `gh` CLI has no stable sub-issue / native-blocking command; text edges are parseable, greppable, and survive CLI churn |
| D-04 | Seven new skills ⇒ count is **41**, and every count claim is derived with `ls -1d .agents/skills/*/ \| wc -l` before writing | The brief's "34→38" counts only the original vendored four; `to-pr`, `close-out`, and `research` are real skill directories too, so any 38 or 40 claim would be false |
| D-05 | `deployer.md` gains **no** `github/*` MCP grant; shell `gh` is sufficient and already granted. The **registry row** is corrected instead | `deployer.md:4-7` grants `edit *` + `shell *`; `gh` 2.98.0 is installed and authenticated. Adding an MCP server to reach `gh` duplicates a working path. Note that the edit/shell permission blocks do **not** govern MCP tool availability, so the row is not provably false — it is corrected because it describes the wrong mechanism, and `reviewer`'s row is left alone for the same reason (nothing proves it wrong) |
| D-06 | `wayfinder`, `to-tickets`, `to-spec`, `close-out` reachability uses **file-read delegation**, not the skill tool | All four are (or will be) `disable-model-invocation: true`, so an agent cannot load them. Precedent already exists: `orchestrator.md:55` tells a sub-agent to read `architecture-blueprint-generator/SKILL.md` and follow it |
| D-07 | **Reversed on 2026-11-02.** The two upstream-documented gaps are **built, not documented**: `research` is vendored and `/setup-matt-pocock-skills` ships | The earlier decision (documentation-only) cost one table row but left `wayfinder` telling users to run a command that does not exist and to call a skill that is not installed. The user reversed it: "close the gap." Option B was costed as "two files plus CLI surface; risk duplicating `npx ai-workflow-setup`" — the risk is answered by CON-12 (the command writes a pointer and labels, nothing else), and the surface is one command file plus one skill file |
| D-08 | The orchestrator gets a new `### Step 2b` section for deliberate skill entries | Step 2a is already 60 lines and is scope-specific; a sibling section keeps the reading order (patterns → scope → deliberate skills → execute) and leaves Step 2a byte-stable |
| D-09 | Version settles to `2.1.0` (minor) with `SKIP_BUMP=1` on every commit in this plan | Adding skills is additive, not breaking (2.x). The husky `post-commit` hook auto-bumps, so the version is set once and re-checked at the end |
| D-10 | The label list is **parsed from `.agents/config/issue-tracker.md`**, not held as a JavaScript constant | A constant plus a doc table is two definitions that drift silently. The doc is the artifact the slash command and every agent can read; the setup phase parses the same table from the **packaged** copy resolved via `new URL('../../.agents/config/issue-tracker.md', import.meta.url)` (not the consumer's cwd, not the consumer's possibly-edited copy). A malformed table is a loud `skipped`, never a wrong label set, and T16 pins the parse of the real file to the six expected names |
| D-11 | The command's only authoring act is the mirror pointer; every tracker fact it reports comes from the canonical doc | With `docs/` never synced (CON-05), a command that pasted the label table into a second file would go stale on the next upgrade. A pointer cannot go stale — it names a path that sync keeps current |

## Execution Notes

- **Hash sequencing (non-negotiable).** Phase 1 writes bytes; Phase 4 hashes them. Any lock write before Phase 1 completes re-introduces the transcription risk this ordering exists to remove. `grilling` is the only existing skill whose hash changes — the other four `v1.3.1` entries keep their bytes and only change `ref`. `research` arrives in the same batch as the other new bytes, so it is hashed in the same late phase, not earlier.
- **One PR, many commits.** Batch commits are expected. Use `SKIP_BUMP=1` throughout and settle `2.1.0` once (T22).
- **Consumer-visible change.** A consumer will receive five new skills, a replaced `grilling`, a new `.agents/config/issue-tracker.md`, a new `.opencode/commands/setup-matt-pocock-skills.md`, and a new Phase 8 during `npx ai-workflow-setup`. Nothing is deleted, and a consumer whose `AGENTS.md` was edited locally will see the existing skip warning rather than the new section (the `.agents/config/README.md` update is the backstop).
- **Built, on purpose (reversed 2026-11-02).** `research` ships and `/setup-matt-pocock-skills` ships; no new agent is added. The command's boundary is one sentence of scope, not code: it writes a pointer and labels, and hands every file distribution question back to `npx ai-workflow-setup` (CON-12).
- **One author for the tracker.** When a requirement seems to need a label table or an operations list somewhere new, add it to `.agents/config/issue-tracker.md` instead, and let the other artifact read it. The command and the setup phase are both readers (CON-11).
