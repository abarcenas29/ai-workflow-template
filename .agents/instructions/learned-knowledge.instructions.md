**New knowledge:**

- **npx-based setup command pattern** (following Playwright, Prisma, Cypress convention) is the future-proof distribution mechanism for CLI tools that need to configure consumer projects
- **Husky v9 programmatic API** is dead simple: `import husky from 'husky'; husky(consumerRoot)` — no need to shell out or manually manage shim files
- **`child_process.spawn` for scripts with `process.exit()`** — importing sync.js (which calls `process.exit()`) directly into the setup process would kill the parent. Spawn as a child process to isolate exit behavior
- **Marker comment idempotency** — a first-line comment (`# Managed by @abarcenas/ai-workflow-template setup`) on hook files enables content-based detection for safe re-runs. This pattern should be used for any managed file that needs idempotent installation
- **6-batch parallel execution worked well**: Batch A (3 foundation: constants, utils, ui) → Batch B (5 core: discover, hooks, prepare, husky-init, sync-phase) → Batch C (2 orchestrator: index.js, bin/setup.js) → Batches D+E (3 config: pre-commit marker, post-merge marker, package.json) → Batch F (4 tests). Clear interface definitions were essential for parallelism
- **Duplicate-marker trap** — constants.js `TEMPLATE_HOOKS.content` must stay in sync with actual `.husky/` hook files. During T12 (post-merge marker), a mismatch was discovered between the template content in constants.js (which already had the marker via `buildHookContent()`) and the actual disk file. Solution: update constants.js template content whenever hook files are modified

**Agent tuning notes:**
- **researcher**: Should explicitly investigate npm ecosystem changes (version-specific behavior, deprecations) — the npm v12 postinstall discovery was the single most important finding that drove the architecture
- **architect**: Modular design with clear interface contracts (Context object shape, return types) paid off — all 5 Batch B modules could be implemented in parallel without coordination issues
- **implementer**: The parallel batch plan with explicit dependency edges (Batch A → B → C, D+E → F) was critical for the 6 sub-agent coder execution. Without this structure, 6 concurrent coders would have had race conditions on shared files
- **coder (parallel batches)**: Batch ordering discipline worked — foundation first, then core, then orchestrator. The truly independent batches (D: markers, F: tests) could run alongside later batches. Key lesson: define interfaces (Context shape, return types) before splitting work across parallel coders
- **unit-tester**: Using real temp directories (`mkdtempSync`) over mocking filesystem operations catches path resolution and permission issues that mocks would miss. Mock only environment-dependent utilities (CI detection, Node version), not filesystem
- **tracker**: Should capture ecosystem discoveries alongside implementation details — the npm v12 finding and marker idempotency pattern are valuable knowledge for future pipeline sessions

## Session: 2026-07-24 — Fix Hook Script References for Consumer Projects

**Pipeline:** researcher → implementer → coder (5 parallel tasks T1–T5) → tracker

**New knowledge:**
- **Hash-based manifest namespace pattern** — `__scripts__/<relPath>` extends the proven `.agents/` (bare path) and `__opencode__/` namespace pattern. The 3-case sync logic (new → copy, untouched → overwrite, locally modified → skip with warning) applies identically across all sync sections. No manifest version schema change needed for adding new namespace keys.
- **Co-location constraint for imported dependencies** — `memory-cli.js` imports `'./memory-index.js'` and `mcp-memory-server.js` also imports `'./memory-index.js'`. Both the consumer-facing script AND its co-located dependency must be in the same sync array. This is an architectural constraint: if you sync one, you must sync all of its relative-import dependencies.
- **`ensureParentDirectory()` handles nested paths automatically** — `mcp/playwright-mcp-launcher.js` lives in a subdirectory, and the existing `ensureParentDirectory()` helper (which calls `mkdirSync(dirname(filePath), { recursive: true })`) creates it without any special handling.
- **`spawnSync` for testing modules with `process.exit()`** — `sync.js` calls `process.exit()` and cannot be imported as a module. The proven pattern: use `child_process.spawnSync` to invoke it as a child process, with `INIT_CWD` pointing to an isolated temp directory (created via `mkdtempSync`), and clean up in `afterAll`. This is the same pattern used by `sync-phase.js` in production.
- **Two Playwright MCP patterns coexist by design** — The template's own root `opencode.json` uses `npx @playwright/mcp@latest` (modern, no file dependency), while `opencode.mcp.example.json` uses the launcher script wrapper with env var configuration (`HEADLESS`, `SLOW_MO`, `VIEWPORT`). Both serve different audiences: the template itself vs. consumer projects that may need launcher configuration.
- **Marker comment for managed-file detection** — The `HOOK_MARKER` (`# Managed by @abarcenas/ai-workflow-template setup`) is the first line of hook files. This enables `discover.js` `isManaged` detection by reading the first line. The marker must be on line 1 for detection to work — the shebang (`#!/bin/sh`) moves to line 2, which is safe because husky sources hook files rather than executing them directly.
- **Relative paths in hooks become valid after script sync — no hook content changes needed** — The key architectural insight: `constants.js` `TEMPLATE_HOOKS` content uses `node scripts/memory-cli.js update` which resolves correctly from the consumer root once `scripts/` exists there. Zero modifications to `constants.js`, `hooks.js`, `.husky/post-merge`, or `.husky/pre-commit` are needed.
- **Content integrity via SHA-256 manifest tracking** — Every synced file is hashed with SHA-256. The manifest tracks `__scripts__/<relPath>` → hash. This enables idempotent re-runs (hash match → no warning), local modification detection (on-disk hash ≠ manifest hash → skip with warning), and force overwrite (`--force` ignores local modifications).
- **Cross-file MCP reference auditing is essential** — 13 reference points across 7 files needed verification (`opencode.mcp.example.json`, `opencode.mcp.json`, `opencode.json` root, `scripts/mcp-memory-server.js`, `scripts/sync.js`, `scripts/sync.test.js`, `.agents-sync-manifest.json`, `docs/playwright-mcp-configuration.md`). Every reference from MCP configs, sync arrays, test assertions, manifest entries, and documentation must be cross-checked to ensure path resolution after sync changes — this is easy to miss.
- **`--force` flag consistency across all sync sections** — The `--force` flag semantics are identical for `.agents/`, `.opencode/`, `__scripts__/`, and root files: it bypasses local modification protection and overwrites. This consistency should be preserved for any future sync sections.

## Session: 2026-07-30

**Pipeline:** Ad-hoc bug fixes (post-knowledgebase-implementation)
**Coverage:** 4 bugs fixed across 3 files; all 158 tests passing after fixes
**TDD Iterations:** 0 (ad-hoc, not pipelined)

**New knowledge:**
- `chunkLearnedKnowledge()` parser bug: regex `[\s\S]*?(?=\*\*|$)` stopped at inline bold markers within bullet content (e.g., `**npm v12 blocks...**`), causing empty content for 4/5 chunks. Fix: use position-based parsing with `indexOf()` + targeted regex `/(?:\n|^)\s*\*\*[^:\n]*:\*\*/m` to find next section header (distinguished by `:**` ending). The key distinction: section headers have `:**` after the bold marker (e.g., `**New knowledge:**`), while inline bold content does not.
- `embed()` returned `Float32Array` which fails `Array.isArray()` in pgvector's `toSql()`, causing all chunks to have null embeddings. Fix: return `Array.from(result.data)` — a plain JS Array that pgvector accepts. `Float32Array` is a typed array, not a standard Array; pgvector's SQL formatter checks `Array.isArray()` and silently inserts null for non-Array values.
- `hooks.test.js` `expectedContent()` was not updated when `buildHookContent()` was fixed (double `HOOK_MARKER` bug). Tests need to stay in sync with code changes — whenever a content-generating function changes, audit all test assertions that reference the generated content.
- Husky v9 deprecation: `. "$(dirname "$0")/_/husky.sh"` is dead in v9+ — the `h` script handles setup natively. MUST remove this line from ALL `TEMPLATE_HOOKS` templates. Failing to remove it causes "File not found" errors in consumer hook execution.
- `knowledgebase-cli.js` never called `dotenv.config()` — `DATABASE_URL` appeared unset even when `.env` had it. All CLI scripts that read `process.env` MUST import `dotenv/config`. This is a universal pattern: any Node.js script that depends on `.env` variables must explicitly load them; `process.env` does not auto-load `.env` files.
- Knowledgebase gap identified: ad-hoc bug fixes not recorded to `learned-knowledge.instructions.md` unless a full feature pipeline runs. The closed-loop workflow has a blind spot for non-pipeline work. Without pipeline orchestration, there is no agent or step responsible for recording learned knowledge.

**Agent tuning notes:**
- When fixing bugs, the coder should ALSO record the root cause + fix to learned-knowledge. Consider adding a `--record` flag or post-fix prompt to the coder agent spec.
- The orchestrator's Step 7 (Persist Lessons Learned) only fires at pipeline end — ad-hoc fixes bypass it entirely. A standalone "record-session" command or hook could fill this gap without requiring the full pipeline machinery.

## Session: 2026-07-30 — MCP Config Rename

**Pipeline:** implementer (bootstrap) → researcher → implementer (planning) → coder → reviewer → tracker
**Coverage:** 109 tests passing across 2 test files (7 sync + 102 setup), 0 regressions, 8 files modified, 1 file deleted
**TDD Iterations:** 0 (feature pipeline, not TDD)

**New knowledge:**
- **Three naming contexts pattern for config renames** — Every config rename involves three distinct naming concerns that must be planned independently: (1) repository/template name (what lives in git, e.g., `opencode.mcp.example.json`), (2) consumer provisioning name (what gets placed on consumer projects, e.g., `opencode.json`), and (3) documentation name (how it's referred to in docs, e.g., `opencode.mcp`). Each may differ and must be tracked separately. In this pipeline, the template name stayed unchanged while the consumer target and documentation references changed independently.
- **`git mv` is not always the right approach for rename + retain** — When a file must remain in the repo under its original name (template source) but the consumer provisioning target changes, do NOT rename the tracked file. Keep the original, update the sync logic to copy to a different target path. The `git mv` approach would change the tracked template when only the consumer output target needs to change.
- **Auto-copy redundancy with single-file patterns** — When a single file serves both template and live roles (eliminating the example/live distinction), the auto-copy step in `sync.js` becomes redundant because the root file sync already copies the template to consumers. Removing the auto-copy simplifies the sync pipeline and eliminates a potential source of drift between the two copies.
- **Corrected-plan note placement is critical** — When user feedback rejects the initial plan approach, place a "Corrected Plan Note" BEFORE the original plan content. It must contain: what was originally proposed, why it was rejected, and the accepted alternative. This ensures coder agents read the correction first and don't follow the rejected approach. In this pipeline, the original `git mv` plan was corrected to "keep template, update sync target only" — and the note at the top of the plan file prevented the coder from executing the wrong approach.
- **`.gitignore` should future-proof against related file spillover** — When removing a specific file entry from `.gitignore`, consider broadening it to cover related naming variants. In this pipeline: `opencode.mcp.json` → `opencode.mcp` (no extension) covers any stray `opencode.mcp*` files in the future.
- **Historical documentation freeze during renames** — Spike docs, archived plans, and historical tracker entries document past state and should NOT be updated during rename operations. Only live documentation (README, activeContext, progress, docs guides) should be updated. Historical files represent snapshots and changing them would erase the audit trail.
- **User correction acceptance loop** — In this pipeline, the user reviewed the researcher output and corrected the approach before the implementer created the plan. The researcher's recommendation was to `git mv opencode.mcp.example.json → opencode.mcp`, but the user identified that the `.example` file should stay (it's the template) and the consumer target should be `opencode.json` (opencode's default config filename). The implementer incorporated this correction into the plan. This is the correct pattern: researcher explores options and recommends, user validates direction before plan creation.

**Agent tuning notes:**
- **researcher**: When auditing references for a rename, categorize ALL hits by change priority: "Must change" (source code, config, sync logic), "Should change" (live documentation, memory bank), "Optional" (historical/spike docs). Include the rationale for each category. Also explicitly list files that do NOT reference the renamed item — this negative confirmation is as valuable as positive hits. And consider including an alternative recommendation section — the user may choose a different approach than the researcher recommends.
- **implementer (planning)**: Always include a prominent "Corrected Plan Note" when user feedback changes the approach. The note should contain: what was originally proposed, why it was rejected, and the accepted alternative. Place it BEFORE the original plan content to ensure coder agents read it first. Also, if the plan diverges significantly from the accepted approach in its detailed tasks, note each divergence explicitly.
- **coder**: When executing a config rename, use the 3-name-context mental model (template name, consumer target name, documentation name) to ensure all changes are internally consistent. Verify each context independently — a change that's correct in one context may be wrong in another. The `.gitignore` entry should future-proof against related file spillover (e.g., `opencode.mcp` covers `opencode.mcp.json`, `opencode.mcp.bak`, etc.).
- **reviewer**: Pre-existing test coverage gaps should be noted separately from issues introduced by the change. A change that is correct but reveals an existing gap is still APPROVED — the gap is a pre-existing concern, not a regression. Use the "pre-existing" label to distinguish.
- **tracker**: The "Three naming contexts" pattern (repo template, consumer provisioning, documentation) is a reusable architectural insight for ANY config rename pipeline. It should be recorded in learned knowledge as a universal pattern, not a one-time fix. Also note the user correction acceptance loop as a pattern — researcher recommends, user validates, implementer incorporates — this validates the confirmation gate architecture.

Because it is still a pure regex with no `new URL()`, the fail-closed-by-construction property is preserved — unparseable tokens remain redacted, `@`-in-password still fully redacted, non-URL messages unchanged. **Universal pattern:** a fail-closed regex can be EXTENDED (add capture groups + callback) without reopening the failure mode that URL parsing introduced.
